# Verification engine: evidence from the fixtures

This file stands in for `.kiro/specs/verification-engine/evidence.md` (task 1). It is kept outside `.kiro/` on purpose. The dump below comes from `bun scripts/dump-cached.ts docs/verify-evidence.md`, which uses `parseWk1` and `decodeRpn` only, plus a plain walk of the record framing to read each stored double's bits straight from the file (a JS runtime may rewrite a NaN payload, so the bits are not taken from the parsed number).

No finding contradicts rule S27, and no KSBASE comparison operand is a label, so nothing here changes the golden counts or stops task 14.

## Answers

**(a) Infinities and NaN.** No cached formula value in any fixture is an infinity. One cached formula value is a NaN: gnome647171-1.wks A5 (below). Six NUMBER input cells in KSBASE.WK1 hold `7ff0000000000000`, positive infinity: G36, G70, C83, D83, C84, D84. Under S27 (WSFF2: sign 0, exponent 7FF, fraction 0) these are ERR values. No formula reads them: the N cells that would compare C83/D83 and C84/D84 (N82, N83, N84) are INTEGER cells, not formulas, and N81 reads only rows 81 and 82. So they cannot change a count. No real file holds the NA pattern (`fff0000000000000`). This agrees with S27; it does not prove the NA half of it, which no fixture exercises.

**(b) KSBASE.WK1 comparison operands.** N3 is `(C3=C4) AND (D3=D4)`, and each other N cell is the same formula one row down. Every C and D operand of all 78 N formulas (rows 3 to 82, read by N3..N81 with N7 missing) is a NUMBER or INTEGER cell. None is a label or empty. So label comparison (U01) does not touch KSBASE, and its 160 formulas stay verifiable as far as operand kinds go. Other details from the dump:

- N7, N82, N83 and N84 are INTEGER cells, not formulas. O7, O82, O83 and O84 read them as plain numbers.
- O84 reads J85, which is empty. As a single reference it counts as 0 (S01).
- The O cells are `IF(Nn=1, 0.5*(Jn+Jn+1), FALSE)` and read only number cells and N cells.

**(c) gnome647171-1.wks A5.** The stored bits are `7ff0ffffffffffff`: sign 0, exponent 7FF, fraction non-zero. WSFF2 names this the STRING pattern, which fits the formula `IF(MOD(A4,2)=1,"Odd","Even")` returning text. The parser reads it as NaN. The engine will compute a string for it, so its reason is `string-result` (requirement 25), and the NaN cached value would also make it `cached-not-a-number` if the result were a number.

## Tolerance sign-off

Measured with `bun run verify:golden` (`tests/differential/verify/golden.json`): on all three real fixtures with formulas, every matched cell is bit-identical to its cached double. The largest relative difference among matched cells is 0 on each file, and `withinTolerance` is 0 everywhere. That includes non-integer results built by real arithmetic, such as KSBASE O3, `0.5 * (J3 + J4)`, cached and recalculated as `3fd01931866a0d7e` (0.25153768659966846).

The sign-off rule asked for the largest difference to be within 1e-12 and well above the double rounding step for at least one real cell. The first half holds. The second cannot: no real cell differs at all, so the corpus gives no measured difference to set the digits from. Nothing here argues for a different number either, so `TOLERANCE` stays at relative 1e-12, absolute 1e-12, on the design's reasoning (a few 80-bit rounding steps per operation over tens of operations), and is not changed to fit the data. `golden.test.ts` pins the measured fact (largest relative difference 0, no within-tolerance matches) so a real file that ever needs the tolerance shows up as a test failure and a review, not a silent pass.
